# 보관료 정산 운영 설계 가이드 — 기간·상태·중간정산·중도출고

> 1인 관리자가 "누가, 어느 기간 보관료를, 냈는지/안 냈는지/얼마 남았는지"를
> 화면 세 번 이내 클릭으로 파악·처리할 수 있게 만드는 실무 운영 설계.
> 현 시스템의 백엔드 자산을 기준으로 "무엇이 이미 있고, 무엇을 어느 화면에 이어야 하는지"를 정의한다.

---

## 0. 결론 요약 (한 문단)

**청구의 단위는 '원장(Ledger) 1건 = 보관기간 1회차'로 이미 올바르게 설계돼 있다.**
원장마다 `기간 시작~종료 + 납기일 + 상태 + 잔액`을 갖고, 부분수금·차월이월·중도출고 일할정산 API까지 백엔드에 존재한다.
따라서 남은 일은 새 모델 설계가 아니라 **(1) '입금예정/연체'를 파생 상태로 화면에 노출, (2) 계약 상세에 회차별 정산 타임라인 추가, (3) 출고 처리에 중도정산을 연결, (4) 연체 필터·부분입금 동선 정돈** — 즉 연결과 노출이다.

---

## 1. 데이터 모델 — 이미 있는 것 (변경 불필요)

```
StorageOrder (계약)          BillingLedger (청구 원장 = 회차)
├─ 보관 시작/종료일           ├─ billingPeriodStart ~ End   ← "언제부터 언제까지의 보관료"
├─ 월 보관료                  ├─ dueDate (납기일)
└─ 상태                      ├─ baseAmount / carriedOverIn(전월이월) / balance(잔액)
                             ├─ status: DRAFT→ISSUED→PARTIALLY_PAID→PAID / CARRIED_OVER / CANCELED
                             ├─ PaymentHistory[] (입금 이력 — 부분입금 지원, 역분개 가능)
                             ├─ BillingAdjustment[] (할인·가산·대손·정정)
                             └─ carriedOverToLedger (미수금이 넘어간 다음 회차 링크)
```

- 매월 1일 02:00 스케줄러가 **활성 계약의 당월 원장을 자동 생성**한다.
- 매일 09:00 **연체 원장 촉구 알림**을 자동 발송한다.
- 중도출고 일할 정산은 `previewMidRelease / applyMidRelease` API가 이미 있다.

**원칙: 이 구조를 그대로 쓴다.** "입금이 어느 기간 것인지"는 별도 매핑 테이블이 아니라
**입금을 원장(=기간)에 귀속시키는 현 구조**가 정답이다. 실무에서 가장 단순하고 분쟁에 강하다.

## 2. 상태 설계 — '입금예정'과 '연체'는 저장하지 말고 파생하라

### 2.1 왜 파생인가

연체를 DB 상태로 저장하면 "자정에 배치가 돌아야 연체로 바뀌는" 시차와, 입금 시 되돌리는 전이 관리가 생긴다.
**연체는 사실이 아니라 시점의 해석**이므로, 조회 시점에 계산하면 항상 정확하고 코드가 사라진다.

### 2.2 화면 표기 규칙 (저장 상태 × 날짜 → 표시 상태)

| 저장 상태 | 조건 | 화면 표기 (뮤티드 팔레트) |
| --- | --- | --- |
| ISSUED / PARTIALLY_PAID | 납기일 ≥ 오늘 | **입금예정** (더스티블루) — 부분수금이면 "부분수금 · 입금예정" |
| ISSUED / PARTIALLY_PAID | 납기일 < 오늘, 잔액 > 0 | **연체 N일** (클레이) — 경과일수를 반드시 함께 |
| PAID | — | 완납 (세이지) |
| CARRIED_OVER | — | 이월마감 (잔액이 다음 회차로 넘어감) |
| DRAFT | — | 작성중 (관리자만 노출) |

> 프론트에 `isOverdue` 파생 로직이 이미 있으므로, "입금예정" 표기와 "연체 N일" 경과일수만 추가하면 된다.

### 2.3 연체의 실무 처리 순서 (권장 운영 룰)

1. **연체 0~7일**: 표시만 (클레이 pill). 매일 아침 자동 촉구 발송이 이미 커버.
2. **연체 7일+**: 청구 화면 상단 "연체" 필터로 모아 보고, 수동 촉구/전화.
3. **월말까지 미수**: 원장을 **차월 이월(CARRIED_OVER)** 처리 → 다음 회차 원장에 `전월이월`로 합산. 미수금이 흩어지지 않고 최신 원장 한 장에 모인다.
4. **회수 불능 판정 시**: 조정(대손상각)으로 마감. 이력이 남아 세무 대응이 된다.

## 3. 화면별 기능 배치 — 어디에 무엇을 넣는가

### 3.1 청구 · 정산 화면 (허브 — 돈의 시점)

현재도 원장 목록·수금·조정·이월이 있다. 보강할 것:

- **[추가] 상태 필터에 '연체'** — 저장 상태가 아니므로 클라이언트 파생 필터로 (잔액>0 & 납기 경과). 연체 건만 모아 아침에 한 번 훑는 동선이 핵심.
- **[추가] 목록에 '보관기간' 컬럼** — `기간시작 ~ 기간종료`를 고객명 옆에. "이 돈이 어느 기간 것인지"가 목록에서 바로 보여야 전화 응대가 된다.
- **[변경] 상태 pill을 2.2 표기 규칙으로** — 발행=입금예정, 연체 N일 표기.
- **[추가] 부분입금 후 남은 잔액을 행에 강조** — `잔액 120,000원 / 청구 300,000원` 형태.

### 3.2 계약 관리 → 계약 상세 (신규: 정산 타임라인 — 고객의 시점)

실무 질문의 8할은 "이 고객 정산 어떻게 돼가?"다. 계약 행 클릭 → 상세 시트에:

```
[정산 타임라인]                        계약: 함유진 · 월 300,000원
● 1회차  1/15 ~ 2/14   완납          300,000 / 300,000   (2/10 입금)
● 2회차  2/15 ~ 3/14   부분수금       200,000 / 300,000   잔액 100,000
● 3회차  3/15 ~ 4/14   연체 12일     0 / 400,000  ← 전월이월 100,000 포함
○ 4회차  4/15 ~ 5/14   (예정)
```

- 백엔드 추가 없이 **원장 목록을 계약(고객) 기준으로 필터**해 그리면 된다 (원장에 order 연결 필드 확인, 없으면 customer 기준).
- 각 회차 클릭 → 기존 원장 상세(입금이력·조정이력)로 이동.
- 여기서 바로 **[입금 기록] 버튼** — 청구 화면까지 안 가고 처리.

### 3.3 출고 처리 모달 (중도출고 정산 — 이미 있는 백엔드를 잇는다)

현재 출고 처리는 날짜만 받고 끝난다. **분쟁이 가장 많은 지점이 여기다.** 보강:

1. 출고 처리 모달에서 실제 출고일 입력 시 → `previewMidRelease` 호출 → **일할 정산 미리보기** 표시:
   `당월 청구 300,000 → 실사용 15일분 150,000 · 환불(또는 차감) 150,000`
2. 관리자가 확인 후 [정산 확정 + 출고] → `applyMidRelease` + 계약 release를 한 트랜잭션 흐름으로.
3. 미수 잔액이 있으면 **"미수 80,000원이 남습니다"** 경고를 모달에 명시 — 출고는 막지 않되(짐은 빼야 하니) 잔액은 원장에 남긴다.

### 3.4 입출고 일정(캘린더) — 시간의 시점

- 납기일 이벤트는 이미 있다. **[변경]** 상태 파생을 2.2 규칙과 통일(연체 N일).
- **[추가]** 청구 이벤트 클릭 → 해당 원장 상세로 이동(현재는 표시만).

### 3.5 대시보드

- **[추가] "이번 주 납기 도래" 카드** — 입금예정 중 납기 7일 이내. 연체를 만들기 전에 잡는 선행 지표.
- 미수금 총액·연체 건수 KPI는 이미 있음.

## 4. 실무 시나리오 → 시스템 동작 매핑

| 시나리오 | 처리 방법 (현 시스템 기준) |
| --- | --- |
| 정상 완납 | 원장 자동 생성(매월 1일) → 발행 → 입금 기록 → PAID. 손댈 것 없음 |
| **부분입금** | 입금 기록에 실제 입금액 입력 → PARTIALLY_PAID + 잔액 자동 계산. 잔액은 같은 원장에 남는다. 다음 입금도 같은 원장에 기록 |
| **기간 지났는데 미입금** | 상태 저장 변경 없음 — 화면이 자동으로 '연체 N일' 표시 + 매일 아침 자동 촉구. 월말에도 미수면 [차월 이월] |
| **중간정산** (몇 달치 몰아서) | 오래된 원장부터 순서대로 입금 기록(원장별 분할 입력). 이월 구조 덕에 보통 최신 원장 1장에 미수가 모여 있어 실제로는 1~2회 입력 |
| **중도출고** | 출고 모달에서 일할 정산 미리보기 → 확정. 환불이면 조정(할인/정정)으로, 추가 청구면 가산으로 원장에 기록 — 현금 흐름과 장부가 일치 |
| 입금 잘못 기록 | 입금 역분개(reversePayment) — 이력을 지우지 않고 취소 레코드를 남긴다 (감사 추적) |
| 보관료 인상/할인 | 다음 회차 원장부터 반영(계약 수정). 당월 소급은 조정으로 |

## 5. 구현 로드맵 (권장 순서 — 각 단계가 독립 배포 가능)

| 순서 | 작업 | 화면 | 난이도 | 효과 |
| --- | --- | --- | --- | --- |
| 1 | '입금예정/연체 N일' 파생 표기 + 연체 필터 + 기간 컬럼 | 청구·정산 | 하 (프론트만) | 미수 관리 즉시 가시화 |
| 2 | 중도출고 정산 미리보기·확정 연동 (`billingApi`에 midRelease 추가) | 출고 모달 | 중 (프론트만, API 존재) | 분쟁 1순위 해소 |
| 3 | 계약 상세 정산 타임라인 + 바로 입금 기록 | 계약 관리 | 중 | 고객 응대 속도 |
| 4 | 납기 도래 카드 | 대시보드 | 하 | 연체 예방 |
| 5 | 캘린더 청구 이벤트 → 원장 상세 딥링크 | 캘린더 | 하 | 동선 단축 |

## 6. 운영 원칙 체크리스트 (금융 장부 관점)

- [ ] 돈은 반드시 **원장(기간)에 귀속**시킨다 — "그냥 얼마 받았다"는 기록 금지.
- [ ] 상태는 저장 최소·파생 최대 — 연체/입금예정은 계산으로.
- [ ] 지우지 말고 뒤집는다 — 입금 취소는 역분개, 금액 정정은 조정 레코드.
- [ ] 미수금은 흩어놓지 않는다 — 월말 이월로 항상 최신 원장 한 장에 모은다.
- [ ] 출고와 정산은 같은 화면에서 — 짐이 나가는 순간이 정산의 마지막 기회다.
